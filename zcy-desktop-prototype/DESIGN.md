# 桌面版技术路线

## 结论

桌面版应该做，但第一版不要内置完整 Chromium，也不要先做复杂 UI。

推荐路线：

- Windows 桌面软件作为控制台。
- 复用用户电脑上的 Microsoft Edge 或 Chrome。
- 使用独立浏览器资料目录保存京东、天猫、政采云登录态。
- 通过 Playwright/CDP 控制浏览器完成采集和发布。
- 图片先进入本地或后台缓存，再上传政采云。

这样比 Electron 自带 Chromium 更轻，也比浏览器插件更可控。

## 为什么不继续主攻插件

插件的问题不是单个选择器错误，而是运行环境不可控：

- 用户当前浏览器登录态不可控。
- 京东、天猫图片懒加载和接口权限变化频繁。
- 后台无登录态访问京东会被跳转到登录页。
- 插件只能依附页面，不能稳定控制完整浏览器流程。
- 采集和政采云发布都依赖页面状态，出错后很难诊断。

桌面受控浏览器可以固定这些变量。

## 最小可行验证

必须先验证三个点，不通过就不进入完整开发：

1. 京东商品采集
   - 目标商品能稳定采到左侧主图列表。
   - 目标商品能稳定采到商品详情图。
   - 稳定采到品牌、型号/货号、商品编号、类目路径、参数文字。
   - 稳定采到销售规格：规格组、全部选项、当前选中项、规格小图。
   - 有货/无货不是核心字段，不作为上传政采云的必填依据。
   - 详情图只读取商品详情模块，不能混入推荐商品、搭配购买、店铺营销图。

2. 政采云发布
   - 能自动选类目。
   - 能自动填品牌、型号、属性。
   - 能自动上传主图和详情图。
   - 能保存草稿或提交。

3. 资源占用
   - 不内置 Chromium。
   - 默认只开一个受控浏览器实例。
   - 空闲时不跑轮询任务。
   - 采集/发布任务串行执行，避免 CPU 和内存飙升。

## 采集架构

京东/天猫采集使用分层策略：

1. 精确组件采集
   - 主图只读取商品主图组件。
   - 详情图只读取商品详情容器。
   - 销售规格只读取规格选择组件。
   - 参数只读取规格参数/属性组件里的文字。
   - 参数图不作为结构化参数来源，优先读取页面里的参数文字。

2. 页面接口和全局变量
   - 读取商品页 JS 变量。
   - 监听当前商品页相关图片请求。
   - 网络资源只能作为当前模块的补充，不能全页面乱扫。

3. 图片缓存
   - 主图下载到本地或后台。
   - 详情图下载到本地或后台。
   - 参数图不作为核心字段处理。
   - 校验尺寸、格式、字节大小。
   - 去重。
   - 记录来源：main、detail、discarded。

## 核心采集输出

采集脚本应输出兼容旧插件和 RPA 的结构化数据，避免后续发布流程再从原始页面数据里猜字段：

- `brand`：品牌。
- `model`：优先型号/货号，其次商品编号或京东 SKU。
- `specs` / `attributes`：产品参数文字字典。
- `selectedSaleSpecs`：当前选中的规格。
- `specGroups`：全部规格组选项。
- `skuSpecs`：旧 RPA 填写 SKU 规格需要的规格组。
- `skuImages`：规格小图。
- `skuData`：当前 SKU 编码、型号和选中规格。
- `images`：商品主图。
- `detailImages`：商品详情图。

## 发布架构

政采云发布不应该只靠“填字段选择器”，而是要做任务状态机：

1. 打开政采云发布入口。
2. 类目选择。
3. 基本信息填写。
4. 关键属性填写。
5. 普通属性填写。
6. 图文信息上传。
7. 销售信息填写。
8. 检测页面错误。
9. 保存草稿或提交。

每一步都要有：

- 成功判断。
- 失败原因。
- 截图/日志。
- 可重试点。

## 软件形态

正式版可以分两层：

- 本地 Agent：控制浏览器、采集、发布、缓存图片。
- 现有 Web 后台：任务中心、授权、草稿管理、配置管理。

前期可以先不做完整桌面 UI，只做一个本地 Agent 和一个简单控制面板。

## 风险

- 政采云页面改版会影响发布自动化。
- 京东/天猫登录风控可能要求人工验证。
- 不同客户账号拥有的政采云类目权限不同。
- 类目和属性规则需要持续维护。

这些风险可以通过受控浏览器、日志、状态机和配置化规则降低，但不能完全消除。
